# 브랜치와 배포 정책

## 브랜치 역할

- `feature/**`: 기능 개발. `develop`으로 PR을 보냅니다.
- `hotfix/**`: 수정 작업. 원칙적으로 `develop`으로 PR을 보내며, 운영 장애만 `main`으로 직접 보낼 수 있습니다.
- `develop`: 다음 운영 버전을 통합하고 검증하는 브랜치입니다. 자동 배포하지 않습니다.
- `main`: 검증된 운영 버전입니다. CI 성공 후 `api.popn.gg`에 자동 배포합니다.

## 일반 출시 흐름

1. `feature/**` 또는 `hotfix/**`에서 작업합니다.
2. `develop` 대상 PR의 CI와 리뷰를 통과시켜 병합합니다.
3. 출시할 변경을 모은 뒤 `develop`에서 `main`으로 PR을 만듭니다.
4. CI와 리뷰를 통과시켜 `main`에 병합합니다.
5. `main` push의 CI가 성공하면 운영 배포가 자동 실행됩니다.

## 긴급 수정

운영 장애로 `hotfix/**`를 `main`에 직접 병합했다면 같은 변경을 즉시 `develop`에도 반영해 두 브랜치가 갈라지지 않게 합니다.

## 필수 검사

- PR 브랜치 흐름 검사
- Gradle 빌드 및 테스트
- MySQL 통합 테스트
- 변경 코드 커버리지 80% 이상
- 배포 manifest 검증
- CodeQL 검사

`develop`의 CI 성공은 운영 배포를 의미하지 않습니다. 운영 배포는 `main`에 병합된 커밋의 CI가 성공했을 때만 실행됩니다.
